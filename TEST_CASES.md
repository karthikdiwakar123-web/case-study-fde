# Test Case Document for Support Ticket Similarity Assistant

This document extends the original basic validation with a deeper semantic-matching assessment based on the case-study brief and the live application behavior.

During the original validation, no application code was changed; small historical
edge-case records were added to the database for semantic coverage. The outcomes
below were recorded before the similarity threshold was lowered from `0.45` to
`0.10`. They document that earlier run and have not all been rerun under the current
threshold, so cases marked as having no result may now return lower-confidence
matches.

The current demo configuration uses `SIMILARITY_THRESHOLD = 0.10` to surface weak
but potentially relevant matches. This improves recall but can produce false
positives; each result should be reviewed rather than treated as a confirmed match.

## Test objective

The main goal was to answer: how intelligent is the app when ticket wording differs but the underlying issue is the same?

Examples of the kinds of scenarios evaluated:

- "chrome not working" vs. "browser tab is blank after login"
- "customer charged twice" vs. "duplicate billing entry"
- "password reset email missing" vs. "reset email never arrives"
- "warehouse connection error" vs. "Snowflake integration failing"
- "revenue chart empty" vs. "dashboard shows no bars"

The result is that the app performs well when the issue is semantically close and the vocabulary overlaps. It is less reliable when the issue is indirect, unusually phrased, or too specific to the historical dataset.

## Detailed semantic observations

### Strong patterns

The app behaves well when the semantic overlap is clear and the wording remains near the same domain:

- Browser blank screen / white screen / dashboard not rendering
- Duplicate billing / charged twice / duplicate invoice
- Reset email missing / no password reset email
- Snowflake connector / warehouse integration failing
- Empty chart / no data / blank revenue report

These cases returned top matches with healthy similarity scores and correctly aligned categories.

### Moderate or weaker patterns

Some issues were recognized but less confidently:

- "App is slow and blank" only reached `0.4651` against a browser issue. It was still related, but not a strong match by the threshold logic.
- "SSO login redirects to blank page" reached only `0.4826` against a generic blank-page login case, which suggests the model is not strongly recognizing SSO-specific wording unless it is present in the historical text.
- "Login still fails after reset" matched a reset-email issue rather than an auth-credential issue, which is still a reasonable but not perfect association.

These outcomes show the app is fairly semantic, but still sensitive to the exact internal vocabulary used in the historical data.

### Clear gaps

The app missed some abstract or indirect issues even when they were conceptually related:

- "Sync job hangs after import" returned no result.
- "Duplicate rows after sync" returned no result.
- "Invoice mismatch in seat count" returned no result.

This is a meaningful learning point: the app is most reliable when a ticket shares explicit terms or a close conceptual pattern with the historical ticket set. It does not yet reason strongly across broader domain abstraction or uncommon phrasing.

## Intelligence assessment

Overall, the application demonstrates decent semantic intelligence for support-ticket similarity.

It is especially good at:

- Recognizing obvious synonyms and wording differences
- Matching similar symptoms within the same functional area
- Ranking likely historical matches above unrelated ones
- Returning resolution notes to help an agent avoid redoing old work

It is less strong at:

- Truly indirect or abstract problem descriptions
- Unusual terms that do not appear in the historical dataset
- Cases requiring deeper business context, rather than symptom similarity

The most important conclusion is that the app is good at "same symptom, different wording" matching, which is exactly the value in the brief. It is not yet a full reasoning engine, but it is effective as a practical retrieval aid for similar tickets.

## Final result

The application passes the core similarity-retrieval requirement and shows good semantic behavior in realistic support-ticket scenarios. It is particularly effective for browser, billing, auth, chart, and warehouse-connectivity cases where the wording is close enough to historical data. It falls short on some more abstract or indirect ticket descriptions, which is expected for a v1 semantic search system and is a reasonable trade-off for the case-study scope.
